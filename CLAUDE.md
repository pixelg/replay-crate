# Replay Crate

Personal Spotify companion: records every play (and podcast listen), counts plays per track, tags genres, manages playlists, and shows listening metrics, for music or podcasts. The work is planned as GitHub milestones (M0–M7 for phase 1, M8–M12 for phase 2, M13 onwards since; M15 is podcasts) on the [project board](https://github.com/users/pixelg/projects/4), which holds every issue. Releases are semver tags (`v0.x` until it's deployed) with a GitHub release each, notes grouped by milestone.

## Layout

pnpm workspace, tasks run by Turborepo (`turbo.json`). Packages export TypeScript source directly (no build step between packages).

| Path | What |
|---|---|
| `apps/web` | Vite SPA: React 19, TanStack Router (file routes in `src/routes`), TanStack Query, Base UI, Tailwind 4, Storybook |
| `apps/api` | Hono API on Node 24, served under `/api/v1` with its OpenAPI 3.1 spec at `/api/v1/openapi.json` and a Scalar reference at `/api/v1/docs`. `createApp()` in `src/app.ts` takes its dependencies as arguments; `src/index.ts` is the server entry |
| `packages/core` | Pure-TS domain logic shared by web, api, and a future React Native app |
| `packages/spotify` | Spotify Web API client and constants |
| `packages/metadata` | Last.fm and MusicBrainz clients (artists' genres) |
| `packages/db` | Drizzle schema + migrations. `createDb()` uses node-postgres for the local Docker Postgres and Neon's HTTP driver for `*.neon.tech`. `@replay-crate/db/testing` gives an in-process PGlite DB |
| `packages/api-client` | Typed Hono RPC client (`hc<AppType>`) + TanStack Query `queryOptions` factories |

## Commands

```bash
pnpm dev                # starts the DB, then web on http://127.0.0.1:5173 + api on :8787 (Vite proxies /api)
pnpm db:up / db:down    # local Postgres 18 in Docker (compose.yaml) on 127.0.0.1:54320
pnpm db:psql            # SQL prompt on the local database
pnpm search:up          # optional Elasticsearch 9 + Kibana (compose profile `search`)
pnpm lint               # oxlint
pnpm typecheck          # tsc in every package
pnpm test               # vitest everywhere; web runs every story as a browser test
pnpm build              # production build of the web app
pnpm serve              # built app + API + scheduled sync on :4173 (the everyday/always-on mode)
pnpm storybook          # component workshop on :6006
pnpm remote:up / remote:down   # going away: Tailscale up + keep the machine awake (systemd-inhibit), and undo
pnpm test:e2e           # Playwright smoke tests: built app + API, in-memory DB, fake Spotify
pnpm --filter @replay-crate/db db:generate   # new migration from schema changes
pnpm db:migrate         # apply migrations to DATABASE_URL
pnpm search:reindex     # rebuild the search index from Postgres (after an Elasticsearch mapping change)
pnpm kibana:load        # import the Kibana dashboards (infra/kibana)
pnpm --filter @replay-crate/db genres --fetch        # refresh the MusicBrainz genre list (then a seed migration)
```

`typecheck`, `test`, `build`, `build-storybook`, `test:e2e` and `dev` go through `turbo run`, so unchanged packages replay cached results (`.turbo/cache`; add `--force` to rerun). A no-op `transit` task chains each package's hash to its workspace dependencies, since they share source rather than build output. Turbo runs tasks in strict env mode: a new env var a task reads must be added to `turbo.json` (`globalEnv` if it changes output, a pass-through list otherwise). `lint` is plain oxlint from the root.

## Conventions

- **Workflow:** never commit to `main` directly. One issue → branch `feat/<issue#>-slug` (or `fix/`, `chore/`) from `main` → **draft** PR with `Closes #n` → merge into `main` when the user says the work is done. CI skips every job on a draft, so push to one freely. Local checks are the gate, not GitHub's: before merging, run `pnpm lint`, `pnpm typecheck` and `pnpm test` (plus `pnpm test:e2e` for changes to the app's flows), then `gh pr ready <n> && gh pr merge <n> --merge --admin` and cancel the PR's CI run; `main` runs CI after the merge as a safety net nobody waits on. When the user wants GitHub's CI on a change, mark it ready and let it run first. Merge commits are fine. Conventional commit messages. New issues go on the project board. Docs-only changes (Markdown files, the licence) may go straight to `main`; CI skips its test jobs for them (the `changes` job in `.github/workflows/ci.yml`), so don't wait on it.
- **Env:** varlock. Values live in the root `.env.local`; each app's `.env.schema` imports what it needs from the root `.env.schema`. Secrets are `@sensitive` and can never reach the web bundle. Read config with `import { ENV } from 'varlock/env'`, never `process.env`. `env.d.ts` files are generated; commit them.
- **Dev host:** always `127.0.0.1`, never `localhost`. Spotify rejects `localhost` redirect URIs, and cookies and the pending login (sessionStorage) are per-origin. The web app moves itself to the origin of `SPOTIFY_REDIRECT_URI` at startup (`src/lib/app-origin.ts`).
- **Auth model:** the API owns every Spotify call and the refresh token (PKCE, no client secret). The browser never holds Spotify tokens. Scopes live in `SPOTIFY_SCOPES` (`packages/spotify/src/constants.ts`); `/auth/me` reports `missingScopes` (requested but not in the user's stored grant) and the app shows a reconnect banner for them, so adding a scope needs no migration. Spotify's grant covers every scope the user has ever given the app, not only the ones asked for at that login.
- **Running modes:** `pnpm dev` (Vite 5173 + API 8787) for development; `pnpm serve` (one origin on 4173, `WEB_DIST_DIR`) for everyday use, optionally as a systemd user service (`scripts/install-service.sh [origin]`). `REPLAY_CRATE_ORIGIN` moves serve mode to another origin, e.g. `https://<host>.<tailnet>.ts.net` behind `tailscale serve` for remote access; it sets `SPOTIFY_REDIRECT_URI` for both the build and the API. Both start the sync scheduler (`SYNC_INTERVAL_MINUTES`), the player watcher for podcast episodes (`PLAYER_WATCH_SECONDS`) and the job runners, and can run at once against the same DB: each holds a lease in `worker_leases` (`apps/api/src/jobs/lease.ts`), so only one process calls Spotify for background work and the other stands by until the lease lapses. The job queue has one lane per outside API (`Handler.api`: `spotify`, `lastfm`, `musicbrainz`), each with its own runner, lease (`jobs`, `jobs:lastfm`, …), pace and daily budget (`LANES` in `jobs/queue.ts`; Spotify's is `JOB_CALLS_PER_DAY`, a token bucket in `call_budgets` keyed by API) and Retry-After, so one API's pause never stalls another. Jobs are reserved atomically (`claim()` in `jobs/queue.ts`), oldest due first except that backfill kinds (`Handler.backfill`: `track`, `artist`) wait behind everything else in their lane, and each makes exactly one call. A 429's Retry-After is stored on the API's row too (`pauseApi()`, or `pauseSpotify()`, in `jobs/budget.ts`) and every background caller of that API, and `POST /history/sync` for Spotify, waits it out: in development mode Spotify can answer a burst with a Retry-After of most of a day. Env-schema changes need a `pnpm dev` restart (`varlock run` reads config at start). Updating the serve service: pull, then `pnpm install` for a new dependency or package, `pnpm db:migrate` for new migrations (before the restart; migrations stay additive so the running code survives them), `systemctl --user restart replay-crate`, and `pnpm search:reindex` for an Elasticsearch mapping change. A restarted process waits up to a minute for the old one's leases to lapse.
- **Charts:** every chart, metric and stat uses [shadcn/ui charts](https://ui.shadcn.com/charts/area) (Base UI flavor, Recharts v3). No hand-rolled charts or other chart libraries.
- **UI:** mobile-first. shadcn/ui (Base UI flavor, `apps/web/components.json`) with our palette on shadcn's token names in `apps/web/src/styles.css`: `bg-background`, `text-muted-foreground`, `bg-card`, `bg-muted`, `bg-primary` (the brand orange), `bg-accent` (subtle hover surface, *not* the brand colour), `text-destructive`, `chart-1..5`. Never raw colours. Light/dark is `data-theme` on `<html>` (set before paint by `index.html`, then `src/lib/theme.ts`); dark tokens and Tailwind's `dark:` key off it, and Storybook has a Theme toolbar. Add shadcn components with `pnpm dlx shadcn@latest add <name>` from `apps/web` (review what it writes); our own Base UI wrappers live beside them in `src/components/ui`. Merge classes with `cn()` from the `cn` package; import from `@/…` or relatively.
- **Stories:** CSF Next (`preview.meta` / `meta.story`, import `preview` from `#storybook/preview`). Every story is a test that must pass its `play` function and the a11y check. Mock HTTP with `beforeEach({ msw }) { msw.use(...) }` using the typed `http` from `src/test/handlers.ts` (openapi-msw over `src/test/api.gen.ts`, generated from the API's spec), never `msw`'s own `http`: paths are the spec's (`/api/v1/tracks/{id}`), and a mock whose path or body drifts from the API fails `pnpm typecheck`. `defaultHandlers` there answers every read with fixtures; the full-app stories start from it. Those are `src/app-<area>.stories.tsx`, one file per area (history, playlists, stats, tracks, player, search, shell, podcasts…), sharing `App` (`src/test/app-story.tsx`) and `src/test/app-story-helpers.ts` (`preloadRoutes()` in every meta's `beforeEach`, so no story waits on a route chunk). A file's stories run one after another and files run in parallel, so add stories to the area they belong to and split a file that grows past a few dozen. `pnpm typecheck` regenerates `apps/api/openapi.json` and `api.gen.ts` first; commit both (CI fails if they're stale).
- **Tests:** API tests call `createApp(...).request(...)` with a PGlite DB from `@replay-crate/db/testing`; no network. The fake Spotify (`apps/api/src/fakes.ts`, no test-framework imports) backs both the unit tests (`testing.ts` wraps it in `vi.fn`) and the E2E server (`apps/api/src/e2e-server.ts`). Its player (`fake-player.ts`) keeps real playback state (devices, item, progress on the test clock, queue, context) and fails the way Spotify does, with `SpotifyApiError.reason` (`NO_ACTIVE_DEVICE`, `PREMIUM_REQUIRED`, …); seed it with `ctx.player.nowPlaying(track)` or `ctx.player.deactivate()`. E2E specs live in `apps/web/e2e`; Playwright intercepts Spotify's authorize page and hands back a code, so the whole PKCE login runs.
- **Routes:** `src/routeTree.gen.ts` is generated by the router plugin on dev/build. Commit it.
- **API routes:** code-first OpenAPI with `@hono/zod-openapi`. Each module builds a router with `createRouter()` (`apps/api/src/lib/openapi.ts`) and declares each endpoint with `createRoute({ tags, operationId, request, responses })`: exactly one tag, with the path under that tag's prefix (`/api/v1/playlists/...` is tag `Playlists`), zod request *and* response schemas, and `...errorResponses('unauthorized', ...)` for every error the handler can return (the typed client's response types come from these). Route definitions sit at module level with `security: signedIn`; the module's factory attaches auth with `.openapi({ ...route, middleware: requireUser(deps) }, handler)`, which types `c.var.user`. Shared response schemas and the `jsonBody` / `jsonResponse` helpers are in `apps/api/src/lib/schemas.ts`; name reusable ones with `.openapi('Name')` so they become spec components. A new error code goes into `ERRORS` with its one status. Modules stay one chain and are mounted with `.route()` in `createApp`, so `AppType` and the spec both see them. `src/openapi.test.ts` fails when a route is undocumented or misfiled, and `src/openapi-conformance.test.ts` calls every endpoint and fails when a response doesn't match its declared schema (or has undeclared fields), so add a call there for each new route.
- **Errors (API):** every error response is JSON `{ error: <code>, ...details }`, declared once in `ERRORS` in `apps/api/src/lib/openapi.ts`: `invalid_request` (400, from the router's `defaultHook`), `unauthorized`, `forbidden`, `not_found`, `reauth_required` (409), `rate_limited`, `internal_error` (500, includes `requestId`). The player adds `no_active_device` (409), `premium_required` (403), `missing_scopes` (403, lists the scopes) and `command_refused` (403, with Spotify's `reason`), mapped from `SpotifyApiError.reason` in `apps/api/src/player/routes.ts`. Every response has `X-Request-Id`; 500s are logged with it.
- **Errors (web):** api-client calls throw `ApiError` (status, code, requestId; status 0 = no response). Anything else thrown is an app bug. `describeError()` in `apps/web/src/lib/describe-error.ts` maps both to what the UI says and offers, and `ErrorPage` is the one error screen: the router's default error component (inside the shell), full-screen for the root, `_app` and `/callback`, plus `AppErrorBoundary` around everything. Use `InlineError` for failed actions that shouldn't take over the page.
- **Imports (M3):** the browser parses the Extended Streaming History (`parseStreamingHistory` in `packages/core`) and uploads only `{ ts, ms, trackId }` per play, and `{ ts, ms, episodeId }` per podcast listen (the export's pause-split stretches joined by `mergeListens`). Keep it that way; the export holds IP addresses, device details and what each episode is called. Plays land in `import_plays` (staging) and move to `plays` once their track is in the catalog: straight away for known tracks, otherwise after the `track` job fetches it (`promote()` in `apps/api/src/imports/service.ts`). A play within `DUPLICATE_WINDOW` of an existing play of the same track counts as a duplicate. The `track` job's 404 handler (`gone`) discards the staged plays and counts them as `unavailable`. Listens stage in `import_listens` and move to `episode_listens` (`promoteListens()` in `imports/listens.ts`) once the `episode` job has the episode, skipping any that overlap a listen the player recorded.
- **Genres (M4):** Spotify reports none, so each artist goes through a chain of jobs (`apps/api/src/genres/jobs.ts`): Last.fm `artist.getTopTags` by name, else MusicBrainz's artist linked to the Spotify id, else a MusicBrainz name search that leaves no doubt, then that artist's MusicBrainz genres. Tags only count when they match the canonical list in `genres` (MusicBrainz's genres, CC0, seeded by migration from `packages/db/src/data/musicbrainz-genres.json` via `packages/db/scripts/genres.ts`), matched on `genreKey()` and weighted by `pickGenres()` in `packages/core`. Results land in `artist_genres`, and `artists.genres_checked_at` marks the lookup (refreshed after 180 days). Nothing enqueues lookups directly: `enqueueGenreLookups()` runs before each round of the genre runner and queues unchecked artists, most recently played first, a batch at a time. The HTTP clients are `packages/metadata`; `LASTFM_API_KEY` is optional (without it, MusicBrainz alone), and MusicBrainz wants `MUSICBRAINZ_USER_AGENT` and one call a second. Search documents carry them too (`genres`, for `genre:` and the Genre facet): a trigger on `artist_genres` queues the artist's documents like a rename (`artist-name`). Tests seed the fakes with `ctx.metadata.tagOnLastfm(name, tags)` / `addToMusicBrainz(...)`, or skip the jobs with `ctx.giveGenres(artistId, names)`. Last.fm's API terms forbid scraping the site and require crediting Last.fm wherever its data shows.
- **Search (M14):** Postgres is the source of truth; the search index is a projection. Triggers (`packages/db/migrations/0010_search_triggers.sql`) record every change that could alter a search document in `search_outbox`; the indexer (`apps/api/src/search/indexer.ts`, running in the API) claims rows by deleting them, rebuilds the affected per-user documents from SQL (`search/docs.ts`) and writes them to the `SearchIndex` in `AppDeps.search` (`search/engine.ts`: Elasticsearch in `search/elastic.ts` when `ELASTICSEARCH_URL` is set, with read/write aliases and external versioning; otherwise Postgres `pg_trgm` in `search_docs`). Shows and episodes are documents too (`show`, `episode`; triggers in `0023_search_podcasts.sql`; an episode's show sits in `artists`, which `show:` matches), and each mode asks for its own types (`MUSIC_TYPES` / `PODCAST_TYPES` in `packages/core`). The query language (`artist:` `genre:` `rating:>=4` `played:2024-09` …) is `parseSearchQuery` in `packages/core`, parsed by both web and API; `genre:` matches whole words in order (`genre:rock` finds art rock, not rockabilly). `played:` matches each document's `playTimes` (every play's time; left out of hits) in the days of the request's `tz`. New searchable data: add it to `docs.ts`, make sure a trigger enqueues its changes, and cover it in `search/contract.ts`, the suite every engine must pass (CI's `search` job runs it on a real Elasticsearch; locally `pnpm search:up` then `ELASTICSEARCH_URL=http://127.0.0.1:9200 pnpm --filter @replay-crate/api exec vitest run src/search`). A mapping change makes a new index hash: run `pnpm search:reindex`. Kibana analytics (`search/analytics.ts`, Elasticsearch only): play events ride the indexer into `rc-plays`, settled searches come in through `POST /search/events` into `rc-search-queries`; the dashboards are code in `infra/kibana/objects.ts` (`pnpm kibana:load`). Tests index with `ctx.indexSearch()`; `pnpm search:reindex` rebuilds from scratch.
- **Recordings (#228):** Spotify lists one recording under a track id per release (single, album, deluxe, remaster), all with the same ISRC. One copy is the recording's canonical track; the others point at it with `tracks.recording_of`. Plays and ratings live only on canonical tracks: triggers move a copy's new plays (keeping Spotify's id in `plays.played_track_id`) and ratings onto it, `merge_recordings(isrcs)` (migration 0025) groups copies and moves what they had, and `upsertCatalog()` calls it when a new copy arrives. So queries grouping `plays.track_id` count recordings with no extra work. Ids from Spotify's own lists (playlist items, what's playing, search results, its top tracks) can be any copy: resolve them with `apps/api/src/tracks/recordings.ts` (`canonicalTrackId`, `recordingsOf`, `recordingId`, `isCopyOf`) before comparing with plays or ratings. Playlist items keep the copy the playlist holds.
- **Podcasts (M15):** a Music | Podcasts mode switches what every screen but the player shows.
  - *Data:* episodes live apart from music (`packages/db/src/schema/podcasts.ts`: `shows`, `episodes`, `episode_listens`, `episode_progress`, `episode_ratings`, `user_shows`, `playlist_episodes`, `player_watch`), so no music query sees them. API modules: `podcasts/` (recording, catalog, followed shows, watcher), `episodes/`, `shows/`, `history/listen-routes.ts`, `stats/podcasts.ts`, `playlists/episode-rules.ts`.
  - *Recording:* Spotify's recently-played never lists episodes, so listens come from looking at the player. Every `GET /player` calls `recordObservation()` (`apps/api/src/podcasts/listens.ts`), which claims the user's `player_watch` row (one recording per 25 s, across processes and tabs) and joins snapshots of one episode into a listen with `mergeListen()` in `packages/core` (carried on while the position moves plausibly within 10 minutes; a paused listen stays open). The background watcher (`podcasts/watch.ts`, every `PLAYER_WATCH_SECONDS`, its own `player-watch` lease) looks at each user's player when the app hasn't lately, so listens are recorded with no browser open. Times are the episode's own (`listened_ms`), so 2× counts what was heard.
  - *Estimates:* listening the app never saw (the phone, with the server off) shows only in Spotify's resume points. `saveResumePoint()` (`podcasts/estimates.ts`), used by the `episode` and `show` jobs, records the difference from the stored progress as a listen with `source = 'estimate'` (`listen_source`), spanning the window it happened in (stored progress's `updated_at`, or for an episode without progress the later of its release and its show's last refresh, never before the app's first `poll` listen) to now. None for moves under 2 minutes, backwards, while the player shows the episode, or when another listen covers the window. Podcast History's Sync (`POST /history/listens/sync`, `refreshFollowedShows()`) refreshes followed shows directly instead of through the queue. An import's listen of the same episode inside an estimate's window replaces it (`promoteListens`).
  - *Lookups:* when the playing episode changes, an `episode` job (ref `userId:episodeId`) fetches it for its release date and the user's resume point (`user-read-playback-position`; Spotify's `fully_played` wins). Followed shows (`user_shows`) come from `GET /me/shows` (`user-library-read`) via `syncFollowedShows()` (`podcasts/shows.ts`): `POST /shows/sync`, and the scheduled sync twice a day. Each show whose latest episodes are older than 12 h gets a `show` job (ref `userId:showId`, `GET /shows/{id}/episodes` with resume points), which feeds `GET /shows/new-episodes`.
  - *Playlists:* episodes sync into `playlist_episodes` beside `playlist_items`, at Spotify's positions (the two together are the playlist in order), so moves use the one position-based `/items/move`; in the web app a move steps between the visible neighbours (`moveTargets()` in `src/lib/playlist-moves.ts`). `GET /playlists?contains=tracks|episodes` is what each mode lists.
  - *Web:* the mode (`music` | `podcasts`) is a per-device view choice in `src/lib/mode.ts` (`rc:mode`, reset to music before every story). The player never depends on it; every other screen does. Mode-aware routes put `mode: getMode()` in their `loaderDeps` and render the mode's page; `useSwitchMode()` (`src/lib/mode-routes.ts`) moves to the counterpart page (`/tracks` ↔ `/episodes`, History keeping its date range) and re-runs loaders. When what's playing is the other kind, `ModeOffer` offers the switch (never on `/player`, never by itself; Settings turns it off, `src/lib/mode-offer.ts`). Podcast queries have their own key roots (`['listens']`, `['episodes']`, `['shows']`). Podcast pieces live in `src/components/podcasts`, and the stats charts, top chart and calendar take either kind of data. Full-app podcast stories are in `src/app-podcasts.stories.tsx`.
  - *Tests:* play episodes with `ctx.player.nowPlaying(episode(...))`; seed `ctx.library.addEpisodes(...)`, `ctx.library.setResumePoint(...)` and `ctx.library.followShow(show, ...episodes)`.

## Spotify Web API constraints (as of Sep 2026)

Development-mode apps were restricted in Feb/Mar 2026. Check these before designing a feature:

- `GET /me/player/recently-played` returns only the last 50 plays, and there's no play-count endpoint. Plays are recorded by polling (M2) and backfilled from the Extended Streaming History export (M3).
- Artist `genres` comes back null; `popularity` and `followers` were removed. Genres come from Last.fm tags with a MusicBrainz fallback (M4).
- Batch lookups (`GET /tracks`, `/artists`, `/albums`) were removed. Fetch one item at a time through the throttled job queue, and cache in the DB.
- Playlist `tracks` became `items` (`/playlists/{id}/items`), and contents are only returned for playlists the user owns or collaborates on. Create playlists with `POST /me/playlists`.
- Recently-played leaves out podcast episodes entirely ("currently doesn't support podcast episodes"). Episodes are seen through `GET /me/player?additional_types=episode` (polled, M15) and the export.
- `GET /episodes` and `GET /shows` (batch) were removed; `GET /episodes/{id}`, `/shows/{id}/episodes` and `/me/shows` remain. A show no longer has `publisher`. Playlist items need `additional_types=episode` to include episodes.
- Search `limit` max is 10.
- Refresh tokens expire 6 months after the user's consent, no matter how often they're refreshed. Handle `invalid_grant` by asking the user to reconnect.
- Dev mode allows 5 users max, and the app owner must have Premium.
